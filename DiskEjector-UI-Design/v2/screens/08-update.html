版本更新

更新只有两个问题：「会不会自己更新」（设置里的一个开关）和 「现在要不要装」（一个弹窗）。弹窗只在自动更新关掉时才会出现—— 开着的时候用户什么都不用做，这正是「后台更新」这个词的含义。 因此这一页里，弹窗和设置行是同一个状态机的两个出口，不是两件独立的事。

A · 有新版本 New version

应用不上架 App Store，只走 Developer ID 直发 —— 所以「能不能替换自身」这件事 没有分叉：能，直接画。弹窗只有这一版：主按钮「后台更新并重启」、次按钮「跳过此版本」， 操作区左边再留一个不占按钮的出口（Esc = 稍后）。

Esc 稍后再提醒

「跳过此版本」和「后台更新并重启」之外，第三个出口是 Esc。 只有这两个按钮时，用户被逼着在「永久跳过这个版本」和「现在就重启」之间二选一 —— 而多数人真正想说的是「现在不方便」。Esc / 关窗 = 稍后再提醒， 这个出口不占按钮，但必须写在操作区左边，否则用户不知道它存在。

B · 设置里的「更新」组 States

弹窗关掉之后，状态必须有落点，否则用户无法判断「刚才那下到底生效没有」。 所有中间状态都就地画在设置这一行上：不弹遮罩、不加横幅、 不往主窗口塞东西 —— 后台更新的全部意义就是别打扰用户。

「稍后」也必须有落点。用户按了 Esc，弹窗消失、什么都没留下的话， 他既不知道有新版本、也没有再打开的入口 —— 只能等下次启动。 这一行把「有新版本」这件事留住，并把按钮从「检查更新」换成「查看更新」（主按钮）， 让用户随时能回到那个弹窗。

百分比是真的，ETA 是编的 —— 所以只画百分比。下载有确定的字节数，进度条说的是实话； 而「还需 1 分钟」在任何网络下都是猜的。（主窗口那条「推出中」不画进度， 理由正好相反：系统的推出接口不提供进度。） 进度条外层固定 16pt，与说明行同高，下载中这一行不会被撑高。

4 · 已就绪 · 待重启安装
更新
1.1.0 已下载完成
重启后完成安装；下次退出应用时也会自动安装。

「重启」不自动做，只提供入口。下载可以完全后台，但重启会关掉用户手上的一切 —— 所以「后台更新并重启」的真实语义是「后台下载，重启时安装」： 下次退出时静默装上，用户想立刻用新版本再点「立即重启」。

检查更新

跳过是一个状态，不是一个动作，所以必须画出来。不写这一行， 「点了跳过 → 下次启动没弹窗」与「检查更新坏了」在界面上长得一模一样 —— 与登录项的「等待系统批准」是同一类错误。 而且它必须可撤销：手动点「检查更新」会清掉跳过标记并重新弹窗， 否则用户只能去改偏好文件才能反悔。

6 · 下载失败 · 不用琥珀也不用红
更新
1.1.0 下载失败
网络不可用。下次启动会自动重试。

这一行不染色。本应用的琥珀只表示「磁盘被占用」、红只表示「破坏性动作」； 下载失败两者都不是。借一个已经承担了别的含义的颜色，比没有颜色更糟 —— 用户会以为磁盘出了问题。失败靠文字 + 一个「重试」按钮表达。

设计说明 Rationale

文案原则

  • 标题写版本号，不写「发现新版本」。用户要判断的是「值不值得为它重启一次」， 所以版本号、当前版本、体积、日期四样都要在首屏给全 —— 与推出弹窗「标题带磁盘名」同一条规则。
  • 按钮用动词，且两个按钮都要能单独读懂。「后台更新并重启」而不是「确定」； 「跳过此版本」而不是「忽略」——「忽略」读不出是忽略这一次还是永远。
  • 说清代价与不代价。「正在推出的磁盘不会被打断」这句是必需的： 用户按下更新前最怕的就是「会不会把我正在拷的东西弄坏」。
  • 「跳过」要说清跳过的范围。「跳过此版本」= 只跳这一个版本，下个版本照常提醒。 设置行里也照写「已跳过 1.1.0」，带上版本号，避免被读成「关掉了更新」。

规格 Handoff

  • 弹窗沿用 .alert：宽 400、圆角 14、材质 blur(34) saturate(180)
  • 图标容器 38 × 38，用 --accent-soft（信息态，不是警告态）
  • 更新日志：12 / 400，行高 1.55，项目间距 6，项目符号 ·
  • 提示块沿用 .callout--info：圆角 6、内边距 9 / 11
  • 操作区：提示文案 11 / --text-3 靠左，按钮靠右、间距 8
  • 设置行内进度条：外层固定 16 高，轨道 5、圆角 999，与磁盘行共用 .meter
  • 更新组在设置面板中排第 4 组（诊断之后、关于之前），面板 480 × 800

这一页对实现提出的要求（不是设计稿能自己满足的）

  • 「后台更新并重启」需要一个真正的更新器。当前 UpdateService 只做 「打开下载页」，没有任何下载与安装代码。要落地本页 B 段的第 3–4 帧（后台下载中 / 已就绪）， 必须先有：下载 + 签名校验 + 替换 bundle + 重启。 两条路：引入 Sparkle（多一个 SPM 依赖、EdDSA 密钥、appcast 托管）， 或自写下载 + 校验。在更新器落地之前，弹窗的主按钮只能退回「打开下载页」 （UpdateService.openUpdateSource() 现在做的就是打开 GitHub Releases）—— 先画上「后台更新并重启」再补实现，用户会点到一个什么都不做的按钮。
  • 「已跳过 1.1.0」需要一个新的持久化键（版本号字符串，不是布尔）。 布尔量表达不了「跳过了哪一个」，而按版本号存才能在 1.2.0 时自动恢复提醒。
  • 「有新版本」是第三种状态，不能用布尔量建模。 「检查完了但没有新版本」与「还没检查过」在界面上都是「没有新版本」， 但它们该显示的文字不同（已是最新版本 vs 尚未检查）—— 必须另有一个「检查是否完成 / 上次检查时间」的位。
  • 「不上架」这个决定把一批渠道分支变成了死代码 —— 已于 2026-09-18 删除。 UpdateService.channel 的 .appStore 分支 （App Store 收据判定、appStoreID、macappstore:// 链接、 「在 App Store 中查看」文案）连同两条本地化键一并移除，渠道只剩 .direct / .development 两种。 「不存在」这件事本身钉了两个测试： UpdateServiceTests/不存在AppStore渠道 从枚举反查 appStore， LocalizationCatalogTests/已删除的AppStore渠道文案不再存在 反查两条文案键 —— 谁加回来谁红。删掉而不是「留作防御」的理由：防御的前提是那条路可能存在， 而 MAS 渠道已经不存在了。
  • 「自动更新」开着时，中间那一段「后台下载中」画不出来（2026-09-19 定案）。 Sparkle 在自动下载那条路上选的是 SPUAutomaticUpdateDriver，而它 一个 user driver 回调都不发：showUpdateFound / showDownloadInitiated / showDownloadDidReceiveData / showReadyToInstallAndRelaunch 这四个回调在全库里只有 SPUUIBasedUpdateDriver 一个调用方，而自动那条路不经过它。 既没有「开始下载」、也没有进度 —— 百分比无从得知，画一条停在 0% 的进度条 比不画更让人怀疑（同 B3 那条「猜出来的百分比会在中途倒退」）。 所以 C 段第 3 行改成了「行保持原样」，第 7 行的触发条件去掉了「自动更新开」。 自动那条路能给出的落点只有一个：delegate 的 willInstallUpdateOnQuit —— 它一到达就已经是「下载完成、等退出时装」。已接上，于是「已就绪」 在自动那条路上是可达的（在此之前它一直停在「已是最新版本」， 而更新其实已经躺在磁盘上等退出 —— 界面在说谎）。 想如实画出中间那一段，得先有一个不带百分比的行态：那是设计决策，尚未拍板。
